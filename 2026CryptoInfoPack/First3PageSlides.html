2) Cryptocurrencies: the shared ledger concept (before blockchain details)

Space reveal points
Traditional finance vs a shared ledger

Traditional finance: each institution keeps its own ledger, requiring reconciliation — creating “multiple versions of truth.”

Traditional many ledgers
Each institution keeps its own ledger, then reconciles later.
Shared ledger one unified view
All participants see the same transaction state (pending/confirmed) without constant reconciliation.
  • Ledger = record of ownership Crypto provides a way to maintain this record across multiple parties.
  • Trust model shift Instead of trusting one institution’s ledger, participants trust rules and validation mechanisms.
  • Why it matters Less “who’s right?” and more “we all see the same record.”
Shared ledger, visualized

Think of a shared “transaction board” everyone can read.

Participant A
Submits a transaction request.
Shared ledger
Stores the agreed state: pending → confirmed (one unified view).
Participant B
Reads the same state and acts on it.
Why it matters
Less “who’s right?” and more “we all see the same record.”

3) What crypto changes (and what banks still do)

Goal: reduce confusion
What crypto changes

Crypto changes how trust and record‑keeping happen. It can replace certain system roles (shared ledger + rule‑based validation), but banks still provide regulatory responsibilities and customer services.

Replaces
Who keeps the record: a shared ledger can become the common reference point.
Does NOT replace
Compliance, risk management, customer onboarding, product design, legal accountability.
  • Replaces: “who keeps the record” Shared ledger can become the common record that parties reference.
  • Banks still provide responsibilities Regulatory responsibilities and customer services (compliance, onboarding, risk, support) still matter.
  • Key takeaway Crypto can improve shared record‑keeping, but banks still run the controls that make it safe.
One sentence to remember

Crypto is not “a bank.”
It’s a different way to build a trusted record and move value — banks still deliver products, compliance, and protection.

Traditional
Trust is institutional + reconciled across separate ledgers.
Crypto-style
Trust is rules + validation on a shared record (plus bank controls around it).

4) What is a blockchain?

Space reveal points
Blockchain = a shared notebook that’s hard to edit.

Think of it like pages in a notebook. Each page “locks” the page before it.

  • Block = a page It contains a list of transactions (who sent what to whom).
  • Chain = pages linked Each block points to the previous block, so the order is fixed.
  • Hard to change history If you change an old block, it breaks the links to every block after it.
Block → Block → Block

A very simplified view (not real cryptography details).

Block 101
Transactions + “fingerprint” of Block 100.
Block 102
Transactions + “fingerprint” of Block 101.
Why it matters
Everyone can check if someone tried to change an old record.

4) Smart contracts: “rules that run” on the shared ledger

Space reveal
What is a smart contract?

A smart contract is shared business logic that runs on a blockchain.
Instead of one party enforcing rules, the network enforces the same rules for everyone.

  • Analogy: “vending machine rules” Put in $2 + choose item → machine releases item automatically. No clerk needed to interpret rules.
  • How it works (high-level) Users submit transactions → contract checks rules → updates shared ledger state (approved / rejected).
  • Why it matters Consistent enforcement + fewer disputes + automation of “if/then” policies across parties.
Open-ended question: If some rules become “code on a shared ledger,” which bank processes could be safer or faster — and which should remain off-chain?
Example smart contract functions (bank-friendly)

These are examples of what “rules that run” can do. (Not technical code — just concepts.)

1) Allowlist transfers policy
Only allow transfers to approved counterparties (addresses/participants).
2) Limits & approvals controls
Enforce transaction limits; require extra approval above threshold.
3) Mint / burn rules supply
Create/destroy tokens only when specific conditions are met (e.g., backed by deposit/liability rules).
4) Escrow & atomic swap settlement
“Either both sides happen, or neither happens” (reduce settlement risk).
Tiny pseudo-logic (illustrative)
IF receiver is allowlisted AND amount <= limit AND approvals >= required THEN transfer & mark confirmed ELSE reject (no ledger update)
Takeaway
Smart contracts = shared rules that automate decisions on the shared ledger.

5) Introducing a blockchain network

Space reveal points
A network is “many computers agreeing on the same notebook.”

Instead of one server updating the ledger, many nodes verify and share updates.

  • Nodes Computers that keep a copy of the blockchain and check transactions.
  • Consensus Rules for how the network decides what is “true” and what gets added next.
  • Finality When the network considers a transaction “done” (no take-backs).
What happens when you send?

Simple flow: create → broadcast → validate → confirm.

You
“Send 10 to Alex” (a transaction request).
Network
Nodes check rules, then add it into a new block.
Result
Everyone’s copy updates to the same state.

6) Two network models: Public vs Private

Space reveal points
Same idea (shared record), different rules (who can join).

Public = open to anyone. Private = only approved members.

  • Public networks Anyone can use it and run nodes. Very transparent.
  • Private networks Only known members can join. Better privacy and governance.
  • Bank-friendly question Do we need openness, or do we need controlled membership + privacy?
Quick comparison

Not “better or worse” — just different trade-offs.

Public
Open access • transparent
Fees can change • global reach
Private
Member-only • privacy controls
Governed rules • faster finality
Key takeaway
Banks usually want strong identity, controls, and audit — so private/permissioned models are common.

8) Tokenized deposits — bridging crypto rails & bank money

Space reveal points
What it is

A tokenized deposit is a bank deposit liability represented as a token. The token moves on a network, but the bank’s core deposit ledger remains the source of truth.

  • 1) Bridge crypto ↔ traditional Use blockchain-style rails (24/7 transfer, shared state, atomic settlement) while keeping money, controls, and legal claim inside the bank (KYC/AML, limits, audit, liability).
  • 2) Reserve backing at mint Minting does not create new money. The bank reserves / ring-fences an equivalent deposit amount (e.g., earmarked balance/control account). No reserve → no mint.
  • 3) Redemption + settlement Redeem = burn token → release reserved deposit. If external parties need fiat, settlement uses existing rails (RTGS/wire/clearing) after burn (or atomically).
Executive takeaway
Bank money on modern rails: tokens move fast, but balances always reconcile to the bank’s books.
Lifecycle (mint → transfer → redeem)

A simple, bank-aligned flow with clear reserve and settlement steps.

Core deposit ledger
Customer/internal funds exist as a deposit balance (bank liability).
Reserve / earmark
Amount is ring-fenced (segregated/earmarked). Prevent double-spend between token + deposit.
Mint token 1:1
Smart contract / policy engine mints deposit-tokens equal to reserved amount. Outstanding tokens must always match reserved deposits.
Token network transfer
Approved members transfer tokens with controls: identity, limits, approvals, audit logs.
Redeem request
Holder requests redemption (internal user, partner bank, or vendor flow via bank).
Burn token
Tokens are burned (destroyed) per policy (and preferably with atomicity to cash release).
Settle funds
Bank releases reserved deposit: (A) internal credit to account, or (B) external payout via existing rails (RTGS/wire/clearing).
Control checkpoint
Continuous reconciliation: tokens outstanding = reserved deposits + full audit trail.

Space reveal points
